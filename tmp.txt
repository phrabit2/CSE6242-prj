**Pinpoint 데이터 흐름 (장애 판단 시 필수 이해)**

```
[대상 서버 JVM]
   └─ Pinpoint Agent (javaagent, 바이트코드 계측)
        │  gRPC push (9991/9992/9993)
        ▼
[88번 Collector]
        │
        ├─→ HBase   : 트레이스(Span) 원본 저장
        ├─→ Kafka   : 지표 스트림
        ├─→ Pinot   : URI Stat / Inspector 집계
        └─→ Zookeeper : HBase·Kafka 코디네이션
        ▼
[88번 Web UI :8080] ← 사용자 브라우저
```

> **핵심**: Agent가 Collector로 **push**하는 구조. Collector가 Agent로 역방향 접속하지 않음.
> → 장애 시 "Agent 쪽 발신 실패"인지 "Collector/Storage 수신 실패"인지 이 방향성으로 먼저 切分.

## 2. 접속 방법

```bash
ssh -o HostKeyAlgorithms=+ssh-rsa -o PubkeyAcceptedKeyTypes=+ssh-rsa wcsadmin@10.194.178.88
```

> ⚠️ **`HostKeyAlgorithms` 옵션 필수.** 서버가 RSA/sha1만 지원하여 옵션 없이는 접속 실패.

### 4.3 ⚠️ Docker Compose 버전 (매우 중요)

| 서버 | Compose 버전 | 명령 형식 |
|---|---|---|
| **10.194.178.88 (본 서버)** | **v2 (플러그인)** | `sudo docker compose ...` (**스페이스**) |
| 10.194.178.89 (Prometheus) | v1 (1.29.2) | `sudo docker-compose ...` (**하이픈**) |

> **v1(하이픈)으로 본 서버를 조작하면 `KeyError: 'ContainerConfig'` / `KeyError: 'id'` 오류가 발생하며, 컨테이너가 좀비 상태로 남아 Docker 네트워크 DNS 해석 실패를 유발합니다.**
> 두 모니터링 서버의 규칙이 서로 다르므로 반드시 구분할 것.

`sudo` 사용 시 플러그인 경로 문제로 `unknown shorthand flag: 'd'` 가 발생하면:

```bash
sudo mkdir -p /usr/local/lib/docker/cli-plugins
sudo cp /data/pinpoint/docker-compose /usr/local/lib/docker/cli-plugins/docker-compose
sudo chmod +x /usr/local/lib/docker/cli-plugins/docker-compose
sudo docker compose version   # 정상 출력 확인
```

### 4.4 Docker data-root 이전 이력

루트 파티션(100GB) 용량 압박으로 Docker 저장소를 대용량 볼륨으로 이전함.

- 이전: `/var/lib/docker` → **`/data/docker`** (`rsync -aP` 사용)
- `/etc/docker/daemon.json` 설정:

```json
{
  "data-root": "/data/docker",
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "100m",
    "max-file": "3"
  }
}
```

> ⚠️ 이전 작업 당시 **Pinot 테이블 데이터가 유실**되어 재생성한 이력이 있음. data-root 재이전이 필요한 경우 반드시 사전 백업할 것.

### 7.3 정책 설계 원칙

- **Pinpoint는 push 방식** → 인바운드를 여는 쪽은 **항상 Collector(88)**. 대상 서버에는 인바운드 개방 불필요.
- ⚠️ **Prometheus(89번 서버)는 pull 방식으로 방향이 정반대**입니다. SG 신청 시 두 제품을 혼동하지 말 것.
  - Pinpoint: `대상 → 88` (인바운드 to 88)
  - Prometheus: `89 → 대상` (인바운드 to 대상)
- Storage(HBase/Kafka/Pinot/Zookeeper)가 88번에 all-in-one으로 구성되어 있으므로 **크로스 서버 포트 불필요**. 향후 스토리지를 분리 배치할 경우 별도 신청 대상.

## 9. Known Issue / 주의사항

### 9.1 ⚠️ com-router (Apache Camel) 트랜잭션 미계측 — **미해결**

| 항목 | 내용 |
|---|---|
| 증상 | `com-router` 애플리케이션의 트랜잭션이 Pinpoint에 수집되지 않음 |
| 원인 | Camel이 `camel-undertow` 로 자체 HTTP 핸들러(`DefaultUndertowHost`)를 기동. Pinpoint의 Undertow 플러그인이 Camel의 `UndertowConsumer.handleRequest` 체인을 후킹하지 못함 |
| 시도한 조치 | `profiler.undertow.enable=true`, `profiler.undertow.deploy.servlet=false` 설정 → 효과 없음 |
| 구조적 한계 | **`pinpoint.config` 는 이미 컴파일된 플러그인의 on/off·튜닝만 가능하며, 신규 계측 대상을 선언할 수 없음.** 설정만으로는 해결 불가 |
| 대안 | ① Camel transport 를 Tomcat 기반으로 전환 ② 커스텀 Pinpoint 플러그인 개발 ③ 설정 기반 커스텀 계측을 지원하는 APM(예: New Relic) 검토 |
| 참고 엔드포인트 | `POST /api/ESP_WCS_REPL_WT_EWM_SEND`, `/wcs/api/inner/com/v1/...` |

### 9.2 HBase Master 기동 실패 복구

볼륨 재생성 등으로 Zookeeper 상태와 HBase 데이터 디렉토리가 불일치하면 HBase Master 가 기동 실패함.

```bash
# 1) Zookeeper 컨테이너 진입 후 hbase znode 삭제
sudo docker exec -it zoo1 bash
zkCli.sh
rmr /hbase
quit

# 2) HBase 데이터 정리
sudo rm -rf /data/pinpoint/hbase/*

# 3) 재기동
cd /data/pinpoint/pinpoint-docker
sudo docker compose up -d pinpoint-hbase
```

> ⚠️ 기존 트레이스 데이터가 삭제됩니다. 최후 수단으로만 사용.

### 9.3 좀비 컨테이너 (해시 접두 컨테이너명)

Compose v1/v2 혼용 시 `<해시>_pinpoint-collector` 형태의 컨테이너가 잔존하며, Docker 네트워크 내 **DNS 해석 실패**를 반복 유발함.

```bash
sudo docker ps -a | grep -E '^[0-9a-f]{6,}_'   # 좀비 확인
sudo docker rm -f <container_id>
sudo docker compose up -d
```

→ 근본 대책: **본 서버에서는 v2(`docker compose`)만 사용** (4.3 참조)

### 9.4 Pinot 관련

- Docker data-root 이전 시 Pinot 테이블 데이터 유실 → 테이블 재생성 필요
- Pinot 노드가 2대 구성이므로 `replicasPerPartition` 을 **3 → 2** 로 조정함. 테이블 재생성 시 동일하게 설정할 것
- 멀티스테이지 쿼리 엔진 활성화: 클러스터 config API로 `pinot.multistage.engine.enabled: true` 설정됨

### 9.5 에어갭 관련

- 일부 컨테이너(특히 mysql 초기화)가 기동 시 GitHub에서 파일을 받으려다 실패할 수 있음 → 해당 기능 미사용 시 컨테이너를 기동하지 않는 방식으로 회피
- Docker 소켓 권한 오류(`permission denied ... docker.sock`) 발생 시: `sudo` 사용 또는 `sudo usermod -aG docker $USER && newgrp docker`

## 11. 기타 항목 (상세 설정 가이드)

> 6~10장에서 참조하는 실무 상세 절차입니다. **인수자가 실제로 손을 대게 될 부분이므로 반드시 숙지 후 작업**하십시오.

### 기타-1. Agent 부착 방법 (systemd)

Pinpoint Agent 는 **애플리케이션 코드 수정 없이** JVM 옵션(`-javaagent`)만으로 부착됩니다.

**① 원본 백업 (필수)**

```bash
sudo cp /etc/systemd/system/wcs.service /etc/systemd/system/wcs.service.bak_$(date +%Y%m%d)
```

**② unit 파일 편집**

```bash
sudo vi /etc/systemd/system/wcs.service
```

`ExecStart` 라인의 `java` 와 `-jar` 사이에 아래 3개 옵션을 삽입합니다.

```
-javaagent:/app/pinpoint-agent-wcs/pinpoint-bootstrap-3.1.0.jar \
-Dpinpoint.agentId=wcs-71 \
-Dpinpoint.applicationName=wcs-backend
```

적용 예시 (wcs-backend, 71번 서버):

```
ExecStart=/usr/bin/java \
  -javaagent:/app/pinpoint-agent-wcs/pinpoint-bootstrap-3.1.0.jar \
  -Dpinpoint.agentId=wcs-71 \
  -Dpinpoint.applicationName=wcs-backend \
  -Dserver.port=8080 \
  -jar /app/wcs/backend/current_wcs.jar --spring.profiles.active=prd
```

> 파일이 readonly 로 열리면 `vi` 에서 `:w!` 로 강제 저장.

**③ 반영 및 재기동**

```bash
sudo systemctl daemon-reload
sudo systemctl restart wcs.service
sudo systemctl status wcs.service
ps -ef | grep javaagent        # 옵션 반영 확인
```

**④ 명명 규칙**

| 항목 | 규칙 | 예시 |
|---|---|---|
| `applicationName` | 애플리케이션 단위 (인스턴스 간 동일) | `wcs-backend` |
| `agentId` | `<앱약칭>-<서버 마지막 옥텟>` (**전체 고유해야 함**) | `wcs-71`, `wcs-72` |

> ⚠️ `agentId` 가 중복되면 Web UI에서 인스턴스가 겹쳐 표시되거나 데이터가 섞입니다.
> ⚠️ `applicationName` 을 인스턴스별로 다르게 주면 Servermap 에서 하나의 서비스로 묶이지 않습니다.

---

### 기타-2. Agent 디렉토리를 JVM 별로 분리하는 이유

**한 서버에서 여러 JVM 을 운영할 경우, Agent 디렉토리를 반드시 애플리케이션별로 분리해야 합니다.**

| 서버 | 애플리케이션 | Agent 디렉토리 |
|---|---|---|
| .71 / .72 | wcs-backend | `/app/pinpoint-agent-wcs` |
| .71 / .72 | com-backend | `/app/pinpoint-agent-com` |
| .71 / .72 | com-router | `/app/pinpoint-agent-route` |

**분리하지 않을 경우 발생하는 문제**

- 여러 JVM 이 동일한 `logs/` 디렉토리에 동시 기록 → **로그 충돌·유실**, 장애 분석 불가
- `pinpoint.config` 를 공유하므로 애플리케이션별 개별 설정(플러그인 on/off, 샘플링률 등) 불가

**디렉토리 생성 절차**

```bash
sudo cp -a /app/pinpoint-agent /app/pinpoint-agent-com
sudo chown -R wcsadmin:wcsadmin /app/pinpoint-agent-com
```

> 실행 계정(`wcsadmin` 등)에 대한 소유권 부여를 누락하면 Agent 가 로그를 쓰지 못해 조용히 실패합니다.

---

### 기타-3. Collector IP 설정 위치 ★ 최다 장애 원인

Pinpoint 3.1.0 은 **profile 기반 설정 구조**(`profiles/release/`, `profiles/local/`)를 사용합니다.
루트의 `pinpoint.config` 만 수정하면 **활성 profile 의 설정이 그대로 남아 기본값 `127.0.0.1` 로 접속을 시도**하며, 서비스는 정상 기동되지만 Pinpoint 에는 나타나지 않습니다.

**① 설정이 박혀 있는 위치를 전부 탐색**

```bash
grep -rn "collector.ip" /app/pinpoint-agent-<앱>/
```

**② 검색된 모든 파일에서 아래 값을 수정**

```properties
profiler.transport.grpc.collector.ip=10.194.178.88
```

**③ 재기동 후 접속 대상 검증**

```bash
sudo systemctl restart <서비스>
journalctl -u <서비스> -n 200 --no-pager | grep -i collector
```

> 로그에 `127.0.0.1:9991` 이 보이면 **설정 미반영** 상태입니다. ①로 돌아가 누락된 파일을 찾으십시오.
> `10.194.178.88:9991` 로 나오면 정상입니다.

---

### 기타-4. 주요 pinpoint.config 설정값

| 설정 | 값 | 설명 |
|---|---|---|
| `profiler.transport.module` | `GRPC` | 3.1.0 기본값. Thrift 로 변경 시 SG 포트가 완전히 달라짐 |
| `profiler.transport.grpc.collector.ip` | `10.194.178.88` | 기타-3 참조 |
| `profiler.span.collected.uri.type` | `RAW` | **실제 URI 경로 표시.** 미설정 시 Spring MVC 템플릿(`/api/{id}`) 형태로만 표시되어 개별 요청 추적 곤란 |
| `profiler.undertow.enable` | `true` | com-router 대상 설정 (단, 9.1 한계 존재) |
| `profiler.undertow.deploy.servlet` | `false` | 상동 |

**Web UI 활성화 기능**

- **Inspector** — CPU / Memory / Heap / GC 등 JVM 리소스 지표
- **URI Stat** — URI 별 응답시간·호출량 통계 (Pinot 기반)
- **Servermap** — 서비스 간 호출 관계도
