두 가지가 얽혔습니다. 하나는 명령 오타, 하나는 grafana 상태 확인.

먼저 그 grep은 -iE에서 하이픈이 빠져서(grep iE '...') iE를 파일명으로 해석한 오류입니다. 결과를 못 본 것뿐이에요. 그리고 datasource.yml은 이제 확실히 깨끗하고 디렉토리에 그거 하나만 있으니, provisioning 원인은 제거됐습니다.

문제는 docker restart grafana로는 부족할 수 있다는 겁니다. grafana가 이미 재시작 루프(Failed 상태)에 빠져 있으면 restart가 깨끗하게 안 먹을 때가 있어요. 컨테이너를 아예 지우고 새로 만드는 게 확실합니다. 그 전에 현재 상태부터 정확히 봅니다.

1) 지금 grafana 상태와 진짜 로그 확인 (오타 수정)
bash
sudo docker ps -a | grep grafana
sudo docker logs grafana --tail 25 | grep -iE 'provision|control|Listen|error'

STATUS가 아직 Restarting인지, 로그에 여전히 control characters가 있는지 봅니다.

로그에 아직 control characters가 있으면 → 컨테이너가 옛 상태를 물고 있는 것 → 아래 2번(재생성)
control characters는 사라졌는데 다른 에러면 → 그 에러가 새 원인
2) 컨테이너 완전 재생성 (restart 말고)

루프 상태를 확실히 털어내려면 지우고 새로 만듭니다:

bash
sudo docker rm -f grafana

sudo docker run -d --name grafana --restart unless-stopped \
  -p 3000:3000 \
  -v grafana_data:/var/lib/grafana \
  -v /data/monitoring/grafana/provisioning:/etc/grafana/provisioning \
  -e GF_SECURITY_ADMIN_USER=admin \
  -e GF_SECURITY_ADMIN_PASSWORD=changeme \
  -e GF_INSTALL_PLUGINS= \
  -e GF_PLUGINS_PREINSTALL_DISABLED=true \
  grafana/grafana:13.1.0

기동은 몇 초 걸리니 넉넉히 기다렸다 확인:

bash
sleep 15
sudo docker ps -a | grep grafana
sudo docker logs grafana --tail 25 | grep -iE 'provision|control|Listen|error'
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:3000/login
확인 포인트
docker ps -a에서 grafana가 Up(Restarting 아님)
로그에 control characters 없음, 대신 HTTP Server Listen(address=[::]:3000) 있음
curl 302

이 세 개가 맞으면 드디어 끝입니다.

그래도 control characters가 또 뜨면

그땐 grafana가 읽는 파일이 정말 이 파일인지 컨테이너 안에서 직접 확인합니다:

bash
sudo docker exec grafana cat -A /etc/grafana/provisioning/datasources/datasource.yml

여기서 제어문자가 보이면 마운트가 딴 파일을 가리키는 것이고, 깨끗한데도 에러면 provisioning 디렉토리 다른 하위 폴더(dashboards 등)에 깨진 yml이 있는 거라 거기까지 확인해야 합니다:

bash
find /data/monitoring/grafana/provisioning -name "*.yml" -o -name "*.yaml" | xargs -I{} sh -c 'echo "=== {} ==="; cat -A "{}"'

우선 2번(재생성) 후 docker ps -a | grep grafana와 curl 결과를 주세요. restart로는 루프가 안 풀렸을 가능성이 커서, 지우고 새로 띄우는 게 이번 핵심입니다. 재생성 후에도 000이면 위 "그래도" 명령으로 grafana가 실제 읽는 파일을 직접 까보겠습니다.

wcsadmin@scp-wcspmq2:/data/monitoring/grafana/provisioning/datasources$ sudo docker ps -a | grep grafana f43da5fab536 grafana/grafana:13.1.0 "/run.sh" 10 minutes ago Restarting (1) 21 seconds ago grafana wcsadmin@scp-wcspmq2:/data/monitoring/grafana

PASTED

찾았습니다. 진짜 범인이 마지막 find 결과에 드러났어요:

=== /data/monitoring/grafana/provisioning/datasources/._datasource.yml ===
^@^E^V^G^@^B^@^@Mac OS X ... com.apple.provenance ...

._datasource.yml — 이게 문제입니다. macOS가 파일을 압축/전송할 때 만드는 AppleDouble 메타데이터 파일(리소스 포크)이에요. 내용이 순수 바이너리(^@, ^E 등 제어문자 덩어리)입니다. Grafana는 datasources 디렉토리의 모든 파일을 provisioning으로 읽으려 하는데, 이 ._ 파일을 YAML로 파싱하려다 "control characters are not allowed"로 죽는 겁니다.

우리가 지금까지 datasource.yml만 봐서 놓쳤고, ls(옵션 없이)로는 ._로 시작하는 숨김 파일이 안 보여서 계속 못 찾았던 거예요. find로 드디어 잡혔습니다. 에어갭 전송(Mac → Drive → ...) 과정에서 딸려온 그 흔적입니다.

해결 — ._ 파일 삭제
bash
cd /data/monitoring/grafana/provisioning/datasources/

# ._ 파일 제거
sudo rm -f ._datasource.yml

# provisioning 디렉토리 전체에 숨어있는 ._ 파일도 싹 정리 (다른 하위폴더까지)
sudo find /data/monitoring/grafana/provisioning -name "._*" -delete

# 확인: datasource.yml 하나만 남고 ._ 없어야 함
ls -la
find /data/monitoring/grafana/provisioning -name "*.yml" -o -name "*.yaml"

find 결과에 이제 ._datasource.yml이 안 나와야 합니다. datasource.yml 하나만.

grafana 재생성
bash
sudo docker rm -f grafana

sudo docker run -d --name grafana --restart unless-stopped \
  -p 3000:3000 \
  -v grafana_data:/var/lib/grafana \
  -v /data/monitoring/grafana/provisioning:/etc/grafana/provisioning \
  -e GF_SECURITY_ADMIN_USER=admin \
  -e GF_SECURITY_ADMIN_PASSWORD=changeme \
  -e GF_INSTALL_PLUGINS= \
  -e GF_PLUGINS_PREINSTALL_DISABLED=true \
  grafana/grafana:13.1.0

sleep 15
sudo docker ps -a | grep grafana
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:3000/login

이번엔 docker ps에서 Up(Restarting 아님), curl 302 가 나와야 합니다. 이번엔 확실합니다 — 죽이던 파일 자체를 제거했으니까요.

prometheus도 복구 필요 (잊지 말 것)

grafana가 뜨면, 아까 v1 up이 터뜨려서 죽은 prometheus 좀비도 정리해야 합니다. 앞선 docker ps -a에서 9de9073f3374_prometheus가 Exited였죠:

bash
# 좀비 제거 후 재생성
sudo docker rm -f 9de9073f3374_prometheus 2>/dev/null

sudo docker run -d --name prometheus --restart unless-stopped \
  -p 9090:9090 \
  -v /data/monitoring/prometheus/prometheus.yml:/etc/prometheus/prometheus.yml:ro \
  -v prometheus_data:/prometheus \
  prom/prometheus:v3.12.0 \
  --config.file=/etc/prometheus/prometheus.yml \
  --storage.tsdb.path=/prometheus
⚠️ 하나 남은 문제 — 컨테이너 간 네트워크

grafana·prometheus를 각각 docker run으로 따로 띄우면 같은 네트워크가 아니라서 grafana가 http://prometheus:9090을 못 찾습니다(compose가 만들어주던 네트워크가 없으니). grafana는 뜨지만 데이터소스 연결은 실패할 거예요. 이건 grafana가 Up 된 걸 확인한 뒤 공용 네트워크로 묶어서 해결하겠습니다:

bash
sudo docker network create monitoring 2>/dev/null
sudo docker network connect monitoring grafana
sudo docker network connect monitoring prometheus

핵심은 ._datasource.yml 삭제입니다. 이게 그동안 ls에 안 보여서 계속 놓쳤던 진짜 원인이에요. 위 순서대로 (._ 제거 → grafana 재생성) 하고 docker ps -a | grep grafana와 curl 결과를 주세요. 302 나오면 prometheus 복구와 네트워크 연결까지 마무리하고, 드디어 터널로 브라우저 접속하시면 됩니다.
